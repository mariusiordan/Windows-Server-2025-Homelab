# Learning Log: 4 November 2026

**Topics:** Connecting GLPI to Active Directory over LDAPS, SSH access, password troubleshooting
**Lab:** SilverBank home lab (Proxmox, domain `corp.silverbank.internal`)

## What I did in the lab

- Tested the GLPI container **from the bottom up**: DNS → TLS → LDAP
- `getent hosts ln-dc01.corp.silverbank.internal` → 192.168.7.80 ✅
- `openssl s_client ... :636` → **`Verify return code: 0 (ok)`** ✅ — the result of the whole chain of fixes (LDAP signing → internal CA → DNS → time zone)
- `ldapsearch` as `svc_glpi` → `result: 0 Success`, all SilverBank users listed ✅
- Added the **SilverBank AD** LDAP directory in GLPI (LDAPS, port 636, filter for active people only) → **Test** all green, 38 entries
- Imported the users with `bin/console ldap:synchronize_users --only-create-new`
- **First employee login:** `james.carter` reached the Self-Service page 🎉

## Problems and how I solved them

| Problem | Cause | Fix |
|---|---|---|
| Forgot the CT 230 root password | No password manager | `pct enter 230` from the Proxmox host (no password needed), then `passwd` |
| `pct` "command not found" | I was already **inside** the container (`root@LN-GLPI01`) | Read the prompt before every command |
| `ssh root@192.168.7.83` → Permission denied | Ubuntu blocks root password login over SSH | Created user `marius` with sudo |
| James can't log in, `data 52e` | Wrong password | Password reset on LN-DC01 |
| Still `52e` after the "reset" | `PasswordLastSet` was **empty** → the reset never saved; also **US keyboard / UK layout** | Reset again with letters and numbers only, verified `PasswordLastSet` |
| Admin `glpi` can't log in | AD is the default Login source, but `glpi` is a **local** account | Login source → **GLPI internal database**; reset the hash in MariaDB |

## Key concepts

- **Test each layer outside the application** — the first failing layer is the problem.
- AD error codes tell you the answer: `52e` = wrong password, `773` = must change, `775` = locked.
- **Verify every change** — `PasswordLastSet`, `Verify return code`, `result: 0` are proof.
- Local accounts (break-glass) vs AD accounts use **different login sources**.
- Named accounts + sudo + SSH keys instead of root.
